# Быстрый разовый сбор: период → поиск → архив

После сохранения всего корпуса обязательна отдельная QA по `prompts/review-research.md`: `qa-research` → сверка источников и контроль пропусков → `research_review.json` → `check-research-qa`. До успешной проверки не переходить к отбору. Время и запросы QA учитывать отдельно от бюджета быстрого сбора; завершение архива не означает готовность исследования. Рабочий QA-промпт читать после сохранения корпуса.

Работай инструментами этой сессии, без разработки нового сборщика, подключения платного API, редактуры и доставки. Прочитай `prompts/common.md`; остальную документацию загружай только для конкретного пробела.

Вход: `run_dir` с manifest, search_plan и снимками конфигов. Если запуска ещё нет, используй явно выбранные даты и создай его через init-run → `plan-search`. Новый период не выбирай. Подтверждённый период и разовый режим повторно не согласовывай. План не исполняет сеть; автономного сборщика в CLI нет. Сессионные примитивы `discovery/session.py` помогают учитывать работу, но не заменяют инструменты поиска/загрузки.

Перед init-run (либо первой операцией существующего запуска) зафиксируй UTC started_at, monotonic и дедлайн +900 секунд. Подготовка кода/инструментов — отдельное setup-время. Первые 60 секунд: диагностика и официальные индексы; до 300: первый проход; до 660: уточнения; до 840: оставшиеся загрузки и сохранение; 840–900: только архив, проверки, отчёт и очередь. Этапы могут перекрываться, их длительности не суммировать как wall time. До сети проверь остаток, timeout и резерв сохранения.

Перед поиском проверь маршрут: manifest.schema_version = 0.5, search_plan.schema_version = 1.1, search_plan.strategy = fast; снимок queries содержит research_policy, search_intents и external_search. Для старого формата создай новый запуск с уже подтверждённым периодом через init-run → plan-search. Не продолжай сбор по старому плану, не подменяй его снимки текущими конфигами и не перезаписывай исторические артефакты. План задаёт задачи; инструменты этой сессии выполняют поиск и загрузку по этому промпту.

1. **Цель.** Ищи конкретное новое событие: кто → что изменил → механика → аудитория/рынок → когда. Учитывай запуски, тесты, расширения, изменения функций/тарифов/правил, ограничения, отключения, откаты и существенные новые раскрытия механик или результатов экспериментов. Приоритет — `research_policy.primary_directions` снимка queries.json: запуски, фичи/тарифы, маркетинговые кампании. Финансы, сделки, назначения и внешние риски — дополнительный поток после основных проверок; допустимы без запуска продукта. Компании и языки бери из снимка. Семь разделов служат классификацией; 14 моделей — словарём уточнений, не квотой поисков. Контекст Lovito нужен только после отбора.
2. **Сначала источники.** Начни с ленты GDI `/category/news/`, затем пройди остальные `source_indexes`: официальные newsroom/IR → другие официальные разделы → ключевые СМИ в порядке source_policy. Один нейтральный URL проверяй один раз сразу по трём направлениям; общий отчёт может дать события нескольких брендов. В подходящих материалах извлекай продуктовые события из всего содержательного текста до определения их приоритета, включая финансовые отчёты, интервью, назначения и партнёрства. Разделяй самостоятельные изменения внутри документа. Для каждого индекса сохраняй запись в raw/source_reviews.jsonl по шаблону source_indexes[].review: status, feed_available, checked_through, end_of_feed, next_page_url, evidence_urls. checked_through означает достигнутую дату публикаций при обходе. Завершённую проверку периода подтверждай достижением его начала либо доказанным концом ленты. Если открылась только главная страница или следующая страница недоступна, фиксируй незавершённый обход и уточняй через source_lookup. Проверенная лента без находок допустима. Пресс-релиз не отменяет медиаобзор. Исторический URL конкретной статьи — `reference_seed`, не независимое обнаружение: для контрольного поиска начинай с нейтрального раздела. Не загружай весь отчёт повторно ради другой компании или темы.
3. **Поиск событий.** После источников выполни короткие открытые `queries[phase=first_pass]`: dating-контекст + запуск/фича/кампания, включая ZH/JA. Они нужны для неизвестных компаний и событий вне известных доменов. Остальные `if_gap` выполняй только с наблюдаемым trigger: непроверенные компания/язык/направление источника, незавершённый период, конкретный сигнал. Бери основное или локальное имя + dating-квалификатор при неоднозначности + одно действие/механику. На компанию/язык план содержит одно условное уточнение; конкретную фичу, кампанию или модель уточняй через followup_templates и слова снимка только по сигналу, не разворачивай все сочетания. Следующий алиас/синоним — при пробеле. Не возвращайся к запросам вида «Tinder news» или «dating app» без действия. Для кампаний используй кампанию/коллаборацию/активацию; для опросов и финансов не требуй launch. Для российских и международных компаний всех групп каталога, а также новых игроков ищи интервью, эксперименты и раскрытые результаты за пределами официальных сайтов. Выполняй external_discovery первого прохода; external_company — только по конкретному сигналу или незавершённой проверке. Через dating_digest.discovery.queries.build_followup_query(plan, language=..., intent=..., company_id=... или company_name=..., term_index=...) выбирай подходящий intent из search_intents и один синоним. Доступны product_change, restrictions, removal, redesign, pricing, migration, interview, experiment_results, disclosure. При пустом или неподходящем ответе используй следующий релевантный синоним. Для внешнего поиска учитывай exclude_domains. Поддержку site, -site, OR и дат проверь; при отсутствии -site используй query_without_domain_exclusions и отбор результатов по доменам. Сохраняй фактические параметры обращения. Отсутствие интервью или результатов за период допустимо.
4. **Компактное покрытие.** Веди две таблицы: компания × предусмотренный язык; источник × три направления. Для проверки нужны query_id/URL, период и наблюдаемый результат: найдено / проверено без находки / ошибка / не выполнено. Упоминание бренда в общем отчёте и наличие задания не доказывают покрытие. Отсутствие новостей по отдельным темам или классам механик за период, особенно за семь дней, допустимо. Проверенный источник без находок не создаёт тематический if_gap. Не вводи обязательный обход классов механик после первого прохода и не запускай поиски ради заполнения всех тем или разделов. Не перемножай компании на семь тем и все модели. Сначала закрывай основные пробелы и локальный язык региональных брендов; дополнительные финансы/риски и уточнения моделей учитывай отдельно. Для выполненного задания проверь все language_variants. Без языкового фильтра нужны разные языковые фразы и наблюдаемый язык результатов. Переиспользовать можно только эквивалентное фактическое обращение: провайдер, текст, фильтры, окно, страница и параметры (`request_key`). Резервируй его до отправки (`WorkLedger.reserve_request`), сохраняй все query_id. Недоступная пагинация — явный пробел.
5. **Отсев до загрузки.** Применяй excluded_domains и noise_rule из retrieval_policy снимка queries.json также к кэшу; исключения журналируй. Используй candidate_filter снимка queries.json, material_filter снимка editorial_policy.json и common.md. Для заголовков доступен `dating_digest.discovery.screening.screen_candidate(title, policy, material_type=...)`; policy — объект candidate_filter, material_type передавай только после классификации по данным. Явные рейтинги лучших сервисов, сравнения, советы по выбору/использованию и общие советы о знакомствах и отношениях, обзоры без события, старые перепечатки и обычные отраслевые афиши/приглашения на вебинары или конференции без новых продуктовых фактов либо результатов исключай с причиной в `raw/rejected_materials.jsonl`. Тип определяй по основной цели и содержанию. Не загружай их полный текст без иной причины. Сомнительное — needs_review и проверка текста; заголовок никогда не доказывает пригодность. Не ставь глобальные -best/-review/-survey: слово может входить в название кампании. Если сравнение упоминает новую фичу, само сравнение исключи, а изменение проверь отдельным источником. Это правило действует также для материалов из СМИ и официальных блогов.
6. **Один URL — одна загрузка.** Общая очередь queued/inflight/fetched/failed (`enqueue` до отправки, затем `claim`). Нормализуй через storage.archive.normalize_url; значимые параметры сохраняй. После redirect/canonical вызывай finish_url, все наблюдения связывай с одной записью. Индекс/RSS — навигация, не статья. Кэш текста максимум 24 часа с collected_at и происхождением; холодный контроль не читает прежний кэш. Изменение текста инвалидирует анализ. Извлекай и анализируй текст один раз по SHA-256 (`remember_analysis`/`cached_analysis`). Не передавай корпус модели повторно.
7. **Сеть и журнал.** Не более четырёх сетевых задач и двух на домен; timeout ≤25 секунд и остатка бюджета, временная ошибка — максимум один повтор. Сначала 1–2 диагностические загрузки; не повторяй массово известный отказ. 403/404 не повторяй одинаково, после двух однотипных отказов домена открывай circuit breaker. Отличай прокси от отказа сайта. Загружай подходящие материалы во время независимого поиска. Журналы пиши программно пакетными checkpoint в UTF-8 JSONL: query_ids, реальные параметры, уникальные call_id/request_key, start/end/duration, статус и компактные URL/title/date_hint; для URL — origin, родители, попытки, HTTP/ошибка, время и cache hit. Держи ответ до подтверждения записи; ошибка записи не повод повторять поиск. Пакетный вызов считается по числу запросов. Отменённые и budget_not_started возвращай в очередь; ошибка не равна пустой выдаче.
8. **Событие и дата.** Подтверди published_at и новый факт по тексту: индексация, dateModified, дата URL и дата упомянутого старого события не заменяют публикацию. Для существенного нового раскрытия механики или результатов исторического теста укажи известную дату реализации и дату раскрытия; не выдавай его за запуск в текущем окне. Свежий анонс будущего запуска маркируй announced. Краткую запись сохраняй в raw/event_candidates.jsonl: actor, company_ids, what_changed, mechanism, markets_or_audience, launch_stage, published_at, source_url, evidence, status. Неизвестное — null/unknown и needs_review; для внешнего риска company_ids может быть пустым. Заметка не заменяет Article JSON и event.schema.json. Сниппет не помечай full. Одно событие/перепечатки объединяй; разные существенные обновления из одного отчёта разделяй. Все подходящие материалы сохраняются до top-10; новые бренды сохраняй в discovery_candidates с названием/алиасами, источниками, датой обнаружения, стадией, рынками, механикой и доказательством новизны по candidate_fields снимка queries.json. Их можно уточнять через company_name до добавления в каталог.
9. **Бюджет.** Цель — 600–900 секунд до сохранённого отчёта; 40–60 поисков с резервом до 80 — гипотеза, не квота и не разрешение скрыть пробелы. Основной резерв трать на три направления, затем дополнительный поток. Последняя минута — сохранение и проверки, без нового сетевого задания. На пределе сохрани очередь и coverage_incomplete с причинами. Setup измеряй отдельно. Меньше запросов не доказывает улучшение качества или скорости.
10. **Обработка и архив.** HTML обрабатывай через общий `dating_digest.ingestion.extract_article(html, metadata, tags=[...])` или `python -m dating_digest extract-page --html <raw.html> --metadata <metadata.json> --output <run_dir>/articles/<id>.json --tags <группы>`. Метаданные: проверенные url, source_id, company_ids, дата и её точность, collected_at; неизвестную дату не угадывай. Сохраняй оригинальный язык, правильный заголовок и очищенный текст по common.md. Проверь содержательные части, условия и ограничения до конца статьи; при признаках обрезки не повышай partial до full по селектору или длине. Теги присваивай по смыслу из разделов снимка editorial_policy; тип страницы не добавляй. UTF-8 Article JSON сохраняй через ArticleArchive.save или archive-articles. Общий article/YYYY/MM/DD.MM.YY/ и _undated не очищай, ID/URL/текст проверяй; изменения получают версии. Сохраняй квитанцию, журналы, две таблицы покрытия, краткие события, причины исключения и очередь. Корпус/индекс/data/ в Git не добавляй.

В отчёте отдельно покажи по приоритетным источникам (включая GDI) чтения, сохранённые статьи и полноту обхода периода. Проверенный источник без находок не проверяй повторно в этом окне и не отключай из-за одного периода. В отчёте покажи полное время до сохранения, фактические поиски отдельно от пакетных вызовов, загрузки/повторы/cache hits, full/partial/неясные даты, основные пробелы и дополнительную очередь. Качество оцени по сохранению релевантных событий исходных cases и отдельных marketing_reference_cases golden set в соответствующем историческом окне, наличию проверенных запусков/фич/кампаний, доле исключённых сравнений/рейтингов и числу загрузок очевидного шума. selection_checks в golden_set — синтетические проверки фильтра, не реальные новости и не доказательство покрытия маркетинга. Исторические reference URL и прошлый корпус сравнивай только после независимого обнаружения; старые публикации не являются полным эталоном live-периода. Отдельно измеренный локальный кэш не доказывает время живого поиска; 10–15 минут и полное покрытие без измерений не заявляй.
