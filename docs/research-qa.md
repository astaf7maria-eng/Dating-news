# Проверка исследования после сохранения JSON

Между `archive-articles` и `prepare-editorial` выполняется отдельная QA. Финальная `review-digest` проверяет уже написанный выпуск и остаётся обязательной. Сбор и QA выполняются в сессии: CLI не вызывает сеть/LLM.

## Рабочий маршрут

1. Сохранить все подходящие Article с оригинальным текстом, происхождение и доказательства даты, причины исключений, наблюдения поиска и покрытия; выполнить archive-articles. raw/event_candidates.jsonl — необязательные заметки без обязательных полей события. Полноценные Event создаются один раз на этапе анализа.
2. `python -m dating_digest qa-research --run-dir data/runs/<run_id>` сохраняет `research_audit.json`. Код 1 означает blocking; код 0 — только успешные локальные проверки, смысловая QA ещё не выполнена.
3. Выполнить common.md + [review-research.md](../prompts/review-research.md) в три прохода: сначала без сети сверить каждый Article и покрытие с сохранёнными оригиналами, метаданными и наблюдениями; затем сделать отдельный короткий контрольный поиск пропусков; после него адресно исправить только найденные пробелы. Все существенные события каждого Article проверяются независимо от будущего выпуска, предварительные карточки не требуются. Достаточные доказательства переиспользовать после содержательной сверки через evidence_refs, без дублирования журналов. Новые наблюдения сохранять в raw/research_verification.jsonl, сетевые обращения с целью и основанием — в raw/qa_search_log.jsonl. Обнаруженные подходящие материалы добавить и проверить обычным маршрутом; архивные версии не переписывать.
4. После последней записи входных данных повторить локальный qa-research для всего запуска и сформировать `research_review.json` по [схеме](../schemas/research-review.schema.json). Смысловую проверку повторять для новых/изменённых материалов и затронутых выводов и целей покрытия, сохраняя оценки всех Article и целей в отчёте. Незатронутые подтверждения переиспользовать; полный сетевой обход и контрольный поиск заново не запускать без нового основания. Отчёт создаёт рецензент; CLI не генерирует прошедший review и не заполняет доказательства.
5. `python -m dating_digest check-research-qa --run-dir data/runs/<run_id>` проверяет отчёт и возвращает eligible_article_paths. Перед отбором выполнять команду заново; использовать только эти статьи. При ошибке продолжать QA, при исчерпанном бюджете сохранить needs_revision и очередь.

Повторное открытие источника нужно при конкретном пробеле: неполный/повреждённый текст, отсутствие сохранённого оригинала для сверки, неподтверждённая дата, противоречие или недостающий первоисточник существенного утверждения. Ошибку извлечения сначала исправляют из сохранённого HTML. Наличие full, хеша или отчёта коллектора не заменяет содержательную проверку.

Контрольный поиск — три запроса всего: по одному на запуски, фичи/тарифы и кампании. Каждый выполняется на одном выбранном языке из снимка плана, с dating-контекстом и без ограничения компанией или официальным доменом. Отдельных серий для новых игроков, внешних публикаций или остальных языков нет. Эти три запроса не доказывают покрытие всех языков каталога. Дальше — только адресные уточнения по конкретным находкам и незакрытому обязательному покрытию, не более трёх обращений на пробел с ранней остановкой. Неразрешённые пробелы сохраняются и препятствуют полному допуску по прежним правилам.

## Что проверяет код

`src/dating_digest/research_qa.py` исполняет Article JSON Schema с проверкой форматов для **всех** articles/*.json и уникальных архивных файлов из квитанции запуска. Проверяются UTF-8/JSON/JSONL, SHA-256 текста, HTTP(S) URL, связи квитанции, наличие архивных тел, ID, целостность снимков и соответствие окна плану. Статьи не изменяются, весь исторический архив не сканируется. Некорректная структура критических артефактов может завершить команду ошибкой до сохранения отчёта.

Неизвестная/внеоконная дата, частичная дневная граница, неполный текст, повреждённая кодировка и диагностика извлечения запрещают eligible, пока карточка не исправлена. Такие статьи можно явно исключить. Прочие замечания о тегах/возможных дублях требуют оценки рецензента. Структурные ошибки блокируют переход независимо от исключения статьи; исправлять через staging и новую архивную версию, не править старые файлы напрямую. ArticleArchive.save и archive-articles проверяют схему до записи; исправления проверяемых метаданных создают версии. Исторические тела сохраняются.

Необязательные заметки, если сохранены, проходят общую проверку JSONL (каждая непустая строка — JSON-объект) и входят в отпечаток raw/. Наличие заметки само по себе не подтверждает факт.

После перехода на необязательные заметки старый `search_plan.json` содержит прежнюю инструкцию `execution_policy.event_notes`. Для продолжения такого запуска перенесите старый план вне папки запуска и заново выполните `python -m dating_digest plan-search --run-dir <run_dir>` из тех же снимков, затем повторите QA. Проверка плана иначе сообщит `plan_content_mismatch`. Статьи, наблюдения и архив повторно собирать не требуется; снимки и старые отчёты автоматически не переписываются. Изменённые правила QA требуют нового `research_review.json`.

Отпечаток включает manifest, план, снимки, подготовленные статьи, квитанцию/индекс, все файлы raw/, связанные архивные тела, правила common/review-research, схемы и код QA. research_audit/research_review не входят в собственный отпечаток. Отчёт должен относиться к текущему набору файлов; добавление/удаление/изменение входа инвалидирует результат и требует актуального локального аудита и отчёта, но само по себе не требует повторных сетевых обращений. Изменение несвязанных исторических статей не требует повторной QA данного запуска.

Gate исполняет схему research-review, запрещает passed с blocking, требует все семь завершённых проверок, ровно одну оценку каждого Article и каждой ячейки из плана. error/not_checked и needs_review не проходят. evidence_refs должны указывать существующие строки raw/*.jsonl с наблюдением источника/поиска; допускаются только checked/completed/assessed/no_results/empty. Наблюдения незавершённых проверок и batch_union_not_per_query отклоняются. Для статьи нужен article_id, для покрытия — target или targets; совпадение бренда в запросе не заменяет явную оценку. Противоречащие eligible результаты наблюдений блокируют допуск. **Соответствие цитаты факту, полнота охвата периода и достоверность итогового вывода остаются смысловой проверкой**; наличие строки журнала не доказывает их автоматически. Программная проверка не заменяет рецензента.

Для нового сбора 1–15 ноября 2026 создавать новый init-run с явными датами `--start-date 2026-11-01 --end-date 2026-11-15`. Снимки старого запуска без research_policy/search_intents/external_search не поддерживают нынешний маршрут; они не изменяются автоматически. В локальном контроле 16.11.2026 все 11 доступных Article JSON архива/staging прошли схему с проверкой форматов. Это проверка совместимости структуры, не дат, содержания или полноты прежнего сбора.

Из образца MI перенесены покрытие, даты, качество источников, фильтры, формат/смысл и проверочный поиск. Адаптация dating сохраняет приоритет официальных первоисточников, локальные языки, интервью/новые раскрытия, допустимость финансов/рисков/маркетинга и пустых тем. Контекст Lovito не используется для допуска и не перепроверяется. Квота публикаций или полный обход всех тем не вводятся. QA имеет отдельное время и число запросов; успех локальных тестов не доказывает полноту живого исследования.
